##Часть 2 — Логи (Loki + Grafana)
Первая попытка поднять Loki для нашей ноды оканчивается неуспехом. По умолчанию Loki пытался поставиться в масштабируемом режиме, для которого нужно внешнее объектное хранилище. Ошибка показана на скриншоте.
![alt text](cashe/image_2_2.png)

Дальше я попробовала переустановить Loki, только теперь уже с указанием необходимых флагов (тот же SingleBinary для решения проблемы масштабируемого режима). Я снова потерпела неудачу. Установщик требовал обязательно добавить флаг (useTestSchema). Как я поняла это система упрощенного хранения тестов для самого Loki (проверка что он работоспособен и корректно принимает логи). На скриншоте сообщение о недостающем флаге.
![alt text](cashe/image_2_3.png)

Тут можно увидеть что Loki успешно запустился и корректно работает в нашей системе. На это указывают 5 подов, которые находятся в состоянии "Running". Сразу ниже показано что агент Alloy точно также успешно запустился и работает. И еще чуть ниже показаны все процессы, что у нас стоит на нашей ноде.
![alt text](cashe/image_2_4.png)

Создаю файл .alloy, где прописывается конфигурация для агента. 
```bash
discovery.kubernetes "pods" { role = "pod" } 
```
спрашивает у Kubernetes про все поды, существующие в кластере. 
```bash
loki.source.kubernetes "pods" { ... }
```
Непосредственно читает логи. targets для каждого пода забирает поток логов. forward_to говорит куда отправлять полученные логи.
```bash
loki.write "default" { ... }
```
Принимает логи и отправляет их уже по установленному url в Loki.

К сожалению в первую попытку произошла безграмотная опечатка - Kybernetes вместо Kubernetes. О чем мне сообщил терминал когда я попыталась получить логи с alloy.
![alt text](cashe/image_2_5.png)

Исправление опечаток помогло, но не сильно. Теперь возникла ошибка - Loki не принимал логи, потому что в файле .alloy не была прописана метка организации. 
![alt text](cashe/image_2_6.png)

Поэтому я добавила строчку tenant_id = "fake", которая по сути является заглушкой для требовательного Loki. После этого все настроилось корректно. Вариант конфигурации агента я вынесла в отдельный файл alloy-config.alloy. Логи читаются и отправляются куда необходимо. Возникла другая проблема - при проверке через curl того, что отображается для лейбла api. Оказывается что в системе его не существует, и в логах выводился пустой результат, потому что лейбл назывался иначе.
![alt text](cashe/image_2_7.png)

С помощью двух команд проверяю какие лейблы реально существуют в нашем Loki. У всех них было одно конкретное значние - loki.source.kubernetes.pods, а не имена подов. Поэтому результат вывода логов был пустым.
![alt text](cashe/image_2_8.png)

Исправляю файл .alloy, добавляя туда discovery.relabel "pod_logs" { targets = ... } с правилами переименования. Для каждого случая мы ставим красивое название. Например __meta_kubernetes_pod_name был назван просто pod. И так с каждым элементом. После этого на скриншоте показано что логи выводятся корректно, со всей необходимой информацией.
![alt text](cashe/image_2_9.png)
